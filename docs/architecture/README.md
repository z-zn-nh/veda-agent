# DS 开发交接文档

这是新项目的开发入口，不是旧项目的产品说明。

## 必读顺序

1. `00-product-boundary.md`：确认产品边界和不可误解的需求。
2. `01-target-architecture.md`：确认宿主、工作区、面板、内容服务和运行时的职责。
3. `02-gui-layout-and-haze.md`：确认 Haze 亚克力风格、顶部工具栏和任意分栏要求。
4. `03-content-and-agent-contracts.md`：确认笔记、白板以及未来 Agent 的占位接口。
5. `04-development-phases.md`：按阶段实施，不要一开始复制旧应用全部代码。
6. `05-acceptance-checklist.md`：每阶段完成前按验收清单检查。
7. `06-legacy-capability-migration.md`：决定旧工程哪些能力可以迁入、哪些不能照搬。
8. `07-layout-design.md`：阶段 2 的落地方案——骨架分区、线框、交互规则、组件映射、布局树 API 变更、验收增补。

## 当前明确结论

- 新项目名称未确定。所有新代码、包名、应用标识、CSS 前缀和持久化 key 使用占位符，不得沿用旧产品名。
- Agent/pi 运行时暂不选定。第一阶段只实现可替换的占位接口，不虚构具体 SDK、RPC 或命令。
- TUI 与 GUI 最终要能查看或接续同一个 Agent 会话；执行器不能由两个界面各自启动。
- 笔记和白板是两个独立工具，分别拥有顶部入口，也可以在没有 Agent 时独立使用。
- 工作区是内容归属单位，可以是代码工作区，也可以只是笔记和白板工作区。
- 白板是独立画布，允许直接创建原生对象，也允许引用笔记。
- 单栏、双栏、多栏都是基础能力，不能只实现固定的 Agent + 工具双栏。
- Haze 是新 GUI 的亚克力视觉基础。Haze 的真实包名、版本和 API 需要开发前确认，不允许凭名称猜 API。

## 开发纪律

- 新项目在独立目录开发，旧工程只作为能力参考和迁移对照。
- 不要把旧应用的整体外壳、总控制器、路由或全局事件原样搬入。
- 先定义接口和验收流程，再接入真实编辑器、画布和持久化。
- 每个阶段都必须说明哪些能力是真实实现、哪些仍是占位。
- 不直接在真实用户数据上试验转换；使用副本和可回滚迁移。
- 未确定的名称统一使用 `AppNamePlaceholder`、`workspaceId`、`paneId`、`sessionId` 等中性名称。

## 当前未决项

- 产品正式名称。
- pi 的具体仓库、分支和版本。
- Agent 运行时采用内嵌、子进程还是独立本地服务。
- GUI 桌面容器和 TUI/GUI 的具体通信方式。
- 白板最终使用 JSON 文件还是数据库。
- 最后一个客户端断开后 Agent 是否继续后台运行。

这些未决项不能阻塞接口设计，但不能被 DS 擅自编造成已经确定的实现。
